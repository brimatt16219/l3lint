# Security review (T-45)

Date: 2026-10-30. Scope: the threat table in the Architecture tab ("Security, privacy and PCI scope"), walked against the code as of WP14. Each row names the control in code, the tests that prove it, and what is still open. Paths are relative to the repository root.

## Summary

The controls hold for card numbers in every output, log privacy, MCP request origins, MCP tool arguments, YAML type tags, alias bombs, duplicate keys, JSON depth, duplicate properties and size limits. The review found seven code gaps (G1 to G7), each with a test in `tests/L3Lint.Security.Tests` or `tests/L3Lint.Fuzz.Tests` that failed until `src` was fixed, and two design gaps (D1, D2). All nine are fixed as of 2026-11-05; the Status column says how, and the tests that failed now pass. A tenth was found on 2026-11-18, when changing a URL shifted the fuzz seeds: a YAML alias that points at its own parent (`&a [*a]`) made `YamlJson.Convert` recurse until the stack overflowed. The converter now limits depth too, with a test (`An_alias_that_loops_back_to_its_parent_is_refused_not_followed`).

Design gaps:

- D1, batch memory (NFR-003). `LintRunner` streams records in, but keeps every `TransactionResult` for the report. Peak working set was 1,131 MB for a 128 MB NDJSON file and 2,463 MB for 256 MB (docs/dev/benchmarks.md). A 1 GB file would need about 10 GB, against the 500 MB target. A hostile or simply large batch can exhaust memory. Fixing it needs a design change (streaming writers, or a capped result set with counts), so it needs an ADR. **Fixed by ADR-0059**: results are kept in compressed blocks and every writer streams; a 1 GB file now peaks at 158 MB (docs/dev/benchmarks.md).
- D2, NDJSON line buffering. `NdjsonLines.ReadAsync` collects a whole line before the per-record size check runs, so one multi-gigabyte line without a newline is held in memory. Stop collecting a line once it passes `maxFileBytes` and report it as too large. **Fixed** (ADR-0059): `NdjsonLines` counts and drops the bytes of an oversized line and the runner reports an input error for its line; `tests/L3Lint.Cli.Tests/NdjsonLinesTests.cs`.

## How the tests run

- `tests/L3Lint.Security.Tests` runs the real CLI entry point in process with the console redirected, in a non-parallel collection, because the console logger writes to `Console.Error` directly. The deep YAML test starts the CLI as a child process, since a stack overflow cannot be caught.
- `tests/L3Lint.Fuzz.Tests` is deterministic (fixed seeds) and kept YAML nesting at or below 300 levels so `dotnet test` itself survived G2 before it was fixed. The long coverage-guided runs are described in `tests/L3Lint.Fuzz/README.md`.
